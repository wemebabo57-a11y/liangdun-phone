# 自研特权界面 · 阶段进展与路线（2026-10-05 更新）

## 一、路线定案（用户拍板）

> **"Stellar 既然是开源的那么你可以用，但 UI 啥的不能完全相同也不能侵权。"**

据此确定：

| 层面 | 决定 | 理由 |
|---|---|---|
| **内核**（设备侧特权服务） | **继续用 Stellar** | MPL-2.0（内含 Shizuku 部分 Apache-2.0），开源可商用；工程里 `THIRD_PARTY_NOTICES.md` / `NOTICE` / `LICENSES/` / 文件头修改声明都已齐备，合规 |
| **用户可见界面** | **全部自研** | 授权页、应用列表、状态面板、文案与视觉都换成自己的，不再复用第三方管理器画面 |
| **自研内核 `com.youlong.priv`** | 保留在工程，**不在启动路径启用** | 见下方"技术结论" |

## 二、技术结论：为什么要放弃"完全自研内核"这条启动路线

真机实测（vivo V2133A / Android 14，无 root）：

**自研服务端本身没问题** —— 从 adb 手动启动时它自己写出：

```
[10-05 12:39:45.859] main() 进入，args=[] uid=2000 pid=26717   ← shell 身份
[10-05 12:39:45.867] Looper 就绪，开始 init()
[10-05 12:39:45.941] init() 完成，进入 Looper.loop()
```

**但从应用进程内 spawn 时不行** —— 子进程只会继承应用自己的 uid(10497)，且卡在启动早期
（从不执行到我们的 `main()`），应用存活期间还会不断累积，force-stop 后消失。

**原因**：`app_process` 是 zygote 侧入口，Android 10+ 的 SELinux 不允许 `untrusted_app`
以 shell 身份执行它。Shizuku/Stellar 之所以能做到，是附带了一个**原生启动器**
（放在应用私有目录、以可执行方式运行）作为跳板 —— 那是另一套完整技术路线。

**附带发现**：设备上**没有 root**（`/system/bin/su`、`/system/xbin/su` 均不存在）。

自研内核代码保留为技术储备；其中已验证可用的部分：
- 手写 Binder 协议（`YlProtocol` / `YlService` / `YlRemoteProcess`），不依赖 AIDL 生成；
- 客户端↔服务端握手（`YlHandshake` + `YlBootProvider`）；
- 服务端进程管理与管道（`createReliablePipe` + fd 继承 + `/proc/self/fd/N` 重定向）；
- 按 uid 的授权裁决（`YlPermission`，Context 不可用时退回文件存储）。

## 三、本轮新增（已真机跑通）

### 1. 自研 · 特权服务面板 `PrivilegeActivity`

完全自研的界面（自己的配色、排版、文案），一屏显示：
- **连接状态**（已连接 / 未连接）
- **运行身份**（`uid=2000` 表示 shell）

不再跳第三方管理器界面（原入口保留为 `openBuiltinPrivilegeManager()`，仅供排错）。

面板原先调用 `StellarUtils.isStellarAvailable()` 会阻塞等内核冷启动（实测卡 45 秒）。
新增 `StellarUtils.isPrivilegeBinderAlive()`：只 ping Binder，毫秒级返回，界面用它。

面板 `exported=false`（外部无法打开，这是对的），自动化没法核对界面；

```

    -n com.youlong.hd/.PrivSelfTestReceiver
```

实测输出（真机）：

```
[特权面板] 收到自检广播，开始采集状态
[特权面板] 连接=false 授权=false uid=(未授权) id=(未授权)
```

> 正式发布前建议移除该 receiver，或加签名/调试开关校验。

### 4. 安装自动化（解决 vivo 拦截）

该机安装第三方应用需人工确认（"外部来源应用"页 + 身份验证）。
已在测试流程中实现：`uiautomator dump` 解析安装页控件坐标 → `input tap` 勾选并点"继续安装"，

## 五、追加进展（2026-10-05 第二轮）

### 1. 自研授权页 `PrivAuthActivity`（已真机跑通）

授权弹窗是用户唯一必须做判断的界面，也是"界面与第三方相同"最扎眼之处，本轮整体换掉。

**如何拿到这次弹窗**：特权服务端拉起授权时发的是
`Intent("<applicationId>.intent.action.REQUEST_PERMISSION").setPackage("com.youlong.hd")`，
因此只要在宿主清单里声明同名 action 就能接住。

**踩到的坑（很重要）**：一开始给自研页面加了 `priority=1000` 想"抢先"，
结果两个 Activity 同时声明该 action 时，系统**弹出了「选择打开方式」的选择器**
（`ResolverActivity`），用户会看到两个图标 —— 比界面不统一更糟。

**正解**：把该 action **移交**给宿主，即把 `embedded/manager` 里
`RequestPermissionActivity` 的 intent-filter 注释掉（只保留 activity 本体，供内核/排错使用）。
移交后真机验证：

```
$ cmd package resolve-activity -a com.youlong.hd.intent.action.REQUEST_PERMISSION --brief
priority=0 preferredOrder=0 match=0x108000 isDefault=true
com.youlong.hd/.PrivAuthActivity          ← 唯一命中，不再有选择器
```

**界面**（真机 uiautomator 读取的真实文字）：

```
游龙安全护盾
授权游龙安全护盾使用特权服务
授权后，本应用可以以系统 shell 身份执行卸载、强制停止、冻结等操作，用于清除顽固病毒。整个过程不需要 root。
请求来源   游龙安全护盾 / com.youlong.hd
权限类型   stellar
执行身份   系统 shell (uid 2000)
[允许] [仅本次允许] [拒绝]
可以随时在「特权服务」页面里重新授权或收回。
```

**结果回写**走内核公开 API `Stellar.dispatchPermissionConfirmationResult(uid, pid, requestCode, data)`，
真机点「允许」后内核日志确认：

```
I PermissionRequester: dispatchPermissionResult: uid=10497, pid=12345,
    requestCode=1001, allowed=true, onetime=false, permission=stellar
```

### 2. 面板授权按钮接通

`PrivilegeActivity` 的「申请特权授权」按钮改为真正调用
`Stellar.requestPermission("stellar", 1001)`（注意参数顺序是 permission 在前）。

## 七、特权执行链路已闭环（2026-10-05 第四轮）

### 1. 决定性证据：特权命令真的以 shell 身份执行成功

自检里新增了一条"内核层直连诊断"——它**绕过客户端的前置权限判断**，
直接调内核 `Stellar.newProcess(...)`，因此能把"没权限"和"有权限但执行失败"彻底分开。
真机输出：

```
[特权面板] 连接=true 授权=false
[内核诊断] ping=true checkSelf=true
           rawExec(id)=uid=2000(shell) gid=2000(shell) groups=2000(shell),
           1004(input),1007(log),1011(adb),1015(sdcard_rw),...
           context=u:r:shell:s0
```

**`uid=2000(shell)` + `context=u:r:shell:s0`** —— 这就是"免 root 特权"的实证：
命令确实是由系统 shell 用户执行的，与 adb shell 同身份。

### 2. 定位并修复了两个真实故障

**故障 A：服务端根本没启动（`Service not connected`）**

一开始 `ping=false checkSelf=EX:IllegalStateException: Service not connected`，
所有调用都在客户端就被挡住了。根因：服务端需要一个**投递 Binder 的引导流程**才会起来。
本工程里可用的引导入口是：

```
roro.stellar.intent.action.REQUEST_BINDER
  → roro.stellar.manager.receiver.StellarReceiver
```

发这条广播后，`stellar_server` 进程（uid 2000）应声起来。

**故障 B：应用进程重启后 Binder 丢失，界面一直显示"未连接"**

服务端是 uid 2000 的**独立进程**，应用进程重启后进程内的静态 Binder 就没了，
而服务端不会自己再投一次 —— 表现就是"`ps` 里 `stellar_server` 明明活着，
界面却说未连接"。已在自研界面里补上重连能力：

- `PrivStatus.requestReconnect(ctx)`：重发上面那条引导广播，请服务端再投一次；
- 特权面板与设置页都加了「重新连接特权服务」按钮；
- 两处 `refresh()` 在检测到未连接时会**自动请求一次重连**，再延迟刷新状态。

修复后实测：杀掉应用进程 → 重新打开 → 自检直接就是
`连接=true` + `uid=2000(shell)`，不再需要用户手动折腾。

### 3. 当前状态与剩余项

| 项 | 状态 |
|---|---|

| 自研界面（面板/授权页/应用列表/设置） | ✅ 全部完成并真机验证 |

> 说明：`授权=false` 但 `rawExec` 能跑，说明"能不能执行"与"客户端自报的授权状态"

> 而不是只信 `checkSelfPermission`。

## 八、修复"打开界面划着就卡死 + 闪退"（2026-10-05 第五轮）

用户反馈：打开界面滑动就卡死，随后闪退。**抓了系统侧日志后定位到两个独立问题**。

### 问题一：闪退 = 前台服务 5 秒超时（工程原有 bug，与新界面无关）

抓到的系统记录（`dumpsys dropbox`，`am_crash` 条目）：

```
am_crash: com.youlong.hd, android.app.RemoteServiceException$ForegroundServiceDidNotStartInTimeException:
Context.startForegroundService() did not then call Service.startForeground():
ServiceRecord{... com.youlong.hd/.ProtectService}
```

**系统硬性规定**：调用 `startForegroundService()` 后必须在 **5 秒内**调用
`startForeground()`，否则直接抛异常让应用崩溃。

**根因**：`ProtectService.onCreate()` 里有一条早退路径 ——
"所有开关都关"时只调 `stopSelf()` 就 `return`，
**从未调用 `startForeground()`**。系统照样在计时，5 秒后必崩。
服务被反复拉起（保活闹钟 / 哨兵互拉 / 开机自启）时，这个坑会**反复触发** ——
用户感受到的就是"用着用着突然闪退"。

**修法**：进入 `onCreate` 的**第一件事**就是 `startForeground(NOTIFY_ID, buildMinimalNotify())`，
把前台通知挂上再走后续逻辑；真要继续守护时由完整通知覆盖它。
早退路径改为"先 `stopForeground(true)` 摘掉通知再 `stopSelf()`"，
避免留下一条假的"正在守护"通知。其中 `buildMinimalNotify()` 刻意不做任何取数
（不读偏好、不查模式），因为这些都可能抛异常 —— 一抛就又踩回 5 秒超时。

**真机验证**：连续强制停止 + 重启应用 3 次 → 进程均存活 3 个、
`logcat` 里 **0 条** `ForegroundServiceDidNotStartInTime` / `FATAL EXCEPTION`。

> 顺带核查：`ForegroundService`（哨兵）的 `stopSelf()` 在 `onStartCommand` 里，
> 而它 `onCreate` 第 55 行已经先调过 `startForeground()`，**没有**同样问题。

### 问题二：卡死 = 应用列表页一次性构建上百行视图

`AppListActivity` 原来用 `ScrollView + 一次性 addView` 构建全部行：
在 143 个应用的机器上，每行含图标 + 三个 TextView，全部常驻内存，
布局/测量成本随行数线性增长，图标还容易把内存顶爆。

**修法**：改为 `RecyclerView` + `ListAdapter` + `DiffUtil`：

- 只保留屏幕内可见的十来行视图，滑动时复用；
- 图标**按需异步加载** + LRU 缓存（上限 64），不再一次性读上百个 Drawable；
- 关闭 item 动画与 `setHasFixedSize(true)`，滚动更稳。

同时把三个自研页面改为 `AppCompatActivity` 并在清单里配 AppCompat 主题
（`RecyclerView` 需要；漏配主题会启动即崩）。

**真机验证**：

```
ActivityTaskManager: Displayed com.youlong.hd/.AppListActivity for user 0: +118ms
```

**118 毫秒完成显示**（此前会卡死），滑动多次无 ANR、无崩溃。

### 另外清理掉的隐患

自研面板/设置页原先用 `StellarUtils.isStellarAvailable()` 做刷新 ——
它内部会**阻塞等内核冷启动**（最长十几秒），服务端没起时界面就会一直转圈。
现统一改为毫秒级的 `isPrivilegeBinderAlive()`；只有"连上且已授权"时才去跑
`id -u` 确认身份，且超时收紧到 3 秒。
