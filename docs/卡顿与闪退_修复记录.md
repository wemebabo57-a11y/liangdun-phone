## 问题一：闪退 —— 前台服务 5 秒内没 `startForeground()`

### 日志证据

`adb shell dumpsys dropbox --print` 里的 `data_app_crash`（2026-10-04 11:56 / 12:06）：

```
Process: com.youlong.hd
android.app.RemoteServiceException$ForegroundServiceDidNotStartInTimeException
Context.startForegroundService() did not then call Service.startForeground():
ServiceRecord{… com.youlong.hd/.ProtectService}
```

Android 规定：`startForegroundService()` 之后服务必须在 **5 秒内**调用
`startForeground()`，否则系统直接杀掉进程（用户看到的就是"闪退"）。

### 根因

`ProtectService.onCreate()` 里有若干**提前 return** 的分支（例如"主开关没开"），
这些分支**没有**调用 `startForeground()` —— 于是只要走到那条分支，
5 秒后系统必定抛 `ForegroundServiceDidNotStartInTimeException` 把 App 干掉。

### 改法（`ProtectService.java`）

1. `onCreate()` **第一件事**就是 `startForeground(...)`，用最简通知
   `buildMinimalNotify()`：
   - 不读 SharedPreferences、不查服务状态、不做任何可能抛异常的调用
     （通知构建里只要抛一次，就等于又回到"5 秒内没 startForeground"）；
   - 之后任何提前 return 的路径都已经处在"前台服务"状态，不会再被系统杀。
2. `buildMinimalNotify()` 里只做常量级操作（channel + Notification.Builder），
   真实状态由后续 tick 里的通知刷新逻辑覆盖。

## 问题二：卡顿 —— 每 4 秒的巡检把主线程按在地上

### 日志证据（应用自己的运行轨迹）

修复后新加的"慢轮次"轨迹，第一条就抓到了现行：

```
[2026-10-05 17:21:12.366] tid=5303 [巡检] 本轮耗时偏长：1816ms
```

（`tid=5303` 是后台线程；改之前这段 1.8 秒的工作是**跑在主线程上的**。）

### 根因

`ProtectService` 的主循环 `tick`（每 4 秒一次）原来整个跑在主线程，而它里面包含：

| 调用 | 代价 |
| --- | --- |
| `virusScanOnce()` | 遍历**全部已安装应用**（真机实测 143~144 个）做病毒库匹配 |
| `scanBlacklistedApps()` | 同样遍历全部应用 |
| `loadWhitelist()` / `loadBlacklist()` | 各读一次 SharedPreferences（磁盘 IO） |
| `monitorPermissionDegrade()` | 读设置项 |
| `ensureVolumeTriggerListener()` | 探针 + 自愈 |

每 4 秒在主线程干一遍，用户滑动时就表现为"一顿一顿、越划越死"。
（列表页另有一个独立问题：`AppListActivity` 一次性构建 143 行，见下。）

### 改法（`ProtectService.java`）

1. **主线程只留毫秒级判断**：`anyTriggerOn()` + 哨兵探活/拉起。
2. **重活全部丢到后台单线程池** `runTickHeavyWorkAsync()`：

   ```java
   private final ExecutorService tickHeavyExecutor =
           Executors.newSingleThreadExecutor(r -> { Thread t = new Thread(r, "protect-tick"); t.setDaemon(true); return t; });
   private final AtomicBoolean tickHeavyRunning = new AtomicBoolean(false);
   ```

   - 单飞保护：上一轮没跑完就直接跳过本轮（病毒库比对在应用多的机器上可能超过 4 秒），
     避免任务堆积；
   - 记一条 `[巡检] 本轮耗时偏长：Nms`（>800ms 才记），以后再卡有据可查。

3. **后台线程里凡是会弹窗的分支，一律 `h.post(...)` 回主线程** —— 这是本次改动最关键的
   安全点：`warnPopup` → `showWarnOverlay`、`startVirusUninstall`、`showVirusAskOverlay`
   都会 `new View` + `wm.addView(...)`，后台线程没有 Looper，
   `ViewRootImpl` 构造会抛 `Can't create handler inside thread that has not called Looper.prepare()`
   —— 那就会从"卡顿"变成"闪退"。

   ```java
   // scanBlacklistedApps()
   final String hitPkg = pkg;
   h.post(() -> warnIfNotRecent(hitPkg, "检测到黑名单应用（" + hitPkg + "）"));
   ```

4. **黑白名单缓存改用并发集合**（`Collections.newSetFromMap(new ConcurrentHashMap<>())`）：
   后台线程 `clear()+add()` 的同时主线程还会 `contains()`，普通 `HashSet` 存在数据竞争。

### 另一个卡顿点：应用列表页（`AppListActivity`）

143 行一次性 inflate + 同步取图标，首帧 `Displayed … +588ms`。
已重写为 `RecyclerView` + `ListAdapter` + `DiffUtil`，图标异步加载 + `LruCache(64)`，
`setHasFixedSize(true)`、去掉 item 动画。

## 排查方法（本机有个坑，务必记住）

**vivo 这台机器上 `adb logcat` 完全看不到本应用的日志**：
`ProtectService` / `AdSkipService` / `MainActivity` 的 tag 一条都不出现，
而系统 tag、其它应用的日志正常。所以：

- ❌ 不要用 `adb logcat | findstr Choreographer` 判断有没有卡顿 —— 永远是空的，会误判成"流畅"；
- ✅ 卡顿看 `adb shell dumpsys gfxinfo com.youlong.hd`（先 `reset` 再操作，然后直接读统计）；
- ✅ 崩溃/ANR 看 `adb shell dumpsys dropbox --print`（过滤 `Process: com.youlong.hd`）；
- ✅ 应用自己的运行轨迹看
  `/sdcard/Android/data/com.youlong.hd/files/crash/probe.txt`
  （内存环形缓冲，**需要触发一次自检才落盘**）：

  ```bash
  adb shell am broadcast -a com.youlong.hd.PRIV_SELFTEST_ENABLE -n com.youlong.hd/.PrivSelfTestReceiver
  adb shell am broadcast -a com.youlong.hd.PRIV_SELFTEST        -n com.youlong.hd/.PrivSelfTestReceiver
  adb shell cat /sdcard/Android/data/com.youlong.hd/files/crash/probe.txt
  ```

  也可直接在页面里点「复制日志发给我」。
