# 紧急逃生"只能触发一次" — 修复记录（2026-10-05）

## 现象

用过 1 次紧急逃生（音量键连按救援）之后，再怎么按都**没有反应**；
重开 App / 重新开启守护就又能用了 —— 典型的"一次性失效"。

## 根因（两处叠加，都在触发侧，弹出逻辑本身没问题）

### ① `countVolumePress()` 里有一道"摇一摇开着就屏蔽音量键"的闸门

```java
// 旧代码（ProtectService.java）
if (getSharedPreferences("shield_prefs", MODE_PRIVATE)
        .getBoolean("shake_trigger_on", false)) {
    return;                     // ← 音量键逃生被整体拦掉，不弹任何提示
}
```

### ② 权限降级会把状态改成"摇一摇开、音量键关"

`monitorPermissionDegrade()`（每 4 秒巡检一次）在**无障碍权限一丢**时：

```java
sp.edit().putBoolean("shake_trigger_on", true).apply();   // 打开摇一摇
...
sp.edit().putBoolean("volume_trigger_on", false).apply(); // 顺手把音量键关掉
```

无障碍恢复时**只还原了音量键开关，摇一摇却留在 true**。
于是 ① 的闸门永久生效：音量键按了有反应（系统音量照常变），但逃生永远不计数 ——
日志里只有一行 `音量键触发暂时不可用`，用户只能重开 App 或重开守护。

### ②′ `MainActivity.startProtect()` 每次都**覆盖用户自己选的触发方式**（真机复现确认）

```java
// 旧代码（MainActivity.java，JS 桥 startProtect()）
prefs.edit()
     .putBoolean("protect_on", true)
     .putBoolean("shake_trigger_on", true)
     .putBoolean("volume_trigger_on", false)   // ← 无条件把音量键关掉
     .apply();
```

界面上的两个开关（音量按键触发 / 摇一摇触发）本来是互斥的、由用户自己选，
`setVolumeTriggerEnabled()` / `setShakeTriggerEnabled()` 会如实写进 prefs；
但只要用户**再点一次「开启实时守护」**（关闭守护后重新打开、触发救援后回到首页都会点），
这段代码就把 `音量键` 强制改回 `false`、`摇一摇` 改回 `true` ——
用户的选择被静默清掉，界面上也不会有任何提示。
这正是用户描述的"**触发一次之后再也触发不了，得重新开启才可以**"：

```
用户开音量键逃生 → 触发一次救援 → 关闭/重开守护 → 音量键被强写 false → 逃生消失
```

这是**本次真机上实际复现到的状态**：装机后读运行轨迹，`[逃生] 守护服务已启动`
显示 `摇一摇=true 音量键=false`，而用户根本没用过摇一摇。

### ③ 附带隐患：音量监听可能"静默脱落"

音量键逃生唯一可靠的入口是挂在无障碍服务上的静态回调
`AdSkipService.setVolumeChangeListener(...)`，而 `ProtectService.onDestroy()`
会把它清成 `null`。一旦出现"清了却没重挂"的时序（系统回收后重建、异常退出、
其它代码误清），逃生就会**完全无响应且日志空白**，同样只能靠重开 App 恢复。

## 改了什么

### `ProtectService.java`

1. **`countVolumePress()`**：保留互斥，但只对"用户自己选的摇一摇"生效；
   权限降级**自动打开**的摇一摇不再屏蔽音量键。

   ```java
   if (shake_trigger_on && !shakeTriggerAutoOnByDegrade && !volume_trigger_on) {
       return;   // 用户选的就是摇一摇 → 尊重，忽略音量键
   }
   if (volume_trigger_on) { ...正常计数... }
   ```

2. **`monitorPermissionDegrade()`**：降级时**不再关闭用户的音量键开关**，
   只把摇一摇当兜底打开，并记下"这是我们自动开的"；权限恢复时按用户原本的
   选择还回去（用户选音量键 → 收掉自动打开的摇一摇；用户没开音量键 → 保留摇一摇，
   避免出现"两个触发都关着"的空窗）。

3. **新增 `ensureVolumeTriggerListener()`**（tick 每 4 秒调用）：
   "用户开着音量键触发 + 无障碍在跑"时核对静态回调是否还在，
   掉了就**原样挂回去**并写一条运行轨迹 —— 逃生不再需要用户重启。

4. **逃生路径加运行轨迹**（`CrashLogger.event`，页面「复制日志」可见）：
   - `[逃生] 音量键达到触发条件（n/N）` —— 计到数了
   - `[逃生] 开始救援：模式=… 音量键触发=… 摇一摇=… 无障碍=…` —— 真进救援了
   - `[逃生] 已跳过：基础模式下前台是系统应用（包名）` —— 故意不弹（避免误判成 bug）
   - `[逃生] 音量键监听曾丢失，已自愈重挂`

   以后再有"没反应"，复制一次日志就能定位卡在哪一步。

### `AdSkipService.java`

新增两个静态方法（配合上面的自愈）：

```java
public static boolean isVolumeListenerRegistered();          // 探针
public static boolean ensureVolumeListener(VolumeChangeListener l);  // 掉了就挂回去
```

### `MainActivity.java`

5. **`startProtect()` 不再覆盖用户的触发方式**：只有用户**从没选过**时才套用
   "默认摇一摇"，选过就原样还原。

   ```java
   final boolean userChoseTrigger = prefs.getBoolean("trigger_mode_user_set", false);
   if (userChoseTrigger) {
       ed.putBoolean("volume_trigger_on", prefs.getBoolean("user_volume_trigger_on", false))
         .putBoolean("shake_trigger_on",  prefs.getBoolean("user_shake_trigger_on", true));
   } else {
       ed.putBoolean("shake_trigger_on", true).putBoolean("volume_trigger_on", false);
   }
   ```

6. **`setVolumeTriggerEnabled()` / `setShakeTriggerEnabled()` 记住"这是用户的选择"**：
   只有值真的发生变化时才写 `trigger_mode_user_set=true` 与 `user_volume_trigger_on` /
   `user_shake_trigger_on`（这两个开关是界面上的 onchange 回调，不存在页面加载回填，
   用 changed 判定只是双保险）。同时各记一条 `[逃生] 用户切换触发方式：…` 轨迹。

### 关于"抓日志"（本机一个重要坑）

vivo 这台机器上 **`adb logcat` 拿不到本应用的任何一行日志**（`ProtectService` /
`AdSkipService` / `MainActivity` 的 tag 一条都不出现，系统 tag 与其它应用正常），
所以**不能用 logcat 判断卡顿和异常**，会误判成"没日志=没问题"。
可用的两条通道：

1. 应用自己的文件轨迹：`/sdcard/Android/data/com.youlong.hd/files/crash/probe.txt`
   （内存里 240 条环形缓冲，**自检/崩溃时才落盘**，所以看完要触发一次刷新：
   `adb shell am broadcast -a com.youlong.hd.PRIV_SELFTEST -n com.youlong.hd/.PrivSelfTestReceiver`，
   且需先 `-a com.youlong.hd.PRIV_SELFTEST_ENABLE` 打开调试开关）；
2. 系统侧无过滤的指标：`adb shell dumpsys gfxinfo com.youlong.hd`（掉帧）、
   `adb shell dumpsys dropbox --print`（崩溃/ANR）。
